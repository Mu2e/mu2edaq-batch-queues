01Cluster access via ssh

The workers sit inside the DAQ enclave and have no direct login. You reach them through the gateway g2gateway01.fnal.gov, using your Fermilab Kerberos ticket. There is no password or ssh-key login.

Step 1

Get a ticket

kinit <username>@FNAL.GOV
klist
Step 2

Log in through the gateway

ssh -J mu2eshift@g2gateway01.fnal.gov \
    mu2ebatch@mu2e-mc1-worker-01.fnal.gov

Optional: add this to ~/.ssh/config, and ssh mc1 is all you need to type.

Host mc1
    HostName mu2e-mc1-worker-01.fnal.gov
    User mu2ebatch
    ProxyJump mu2eshift@g2gateway01.fnal.gov
    GSSAPIAuthentication yes
    GSSAPIDelegateCredentials yes

Windows 11: the built-in OpenSSH client supports -J. Kerberos is simplest from WSL2: run kinit and ssh inside the Linux shell.

02Login accounts

Batch work runs under shared Mu2e accounts, not personal ones. You can log in to an account if your Kerberos principal is listed in its ~/.k5login.

AccountUse it forSubmit jobs
mu2ebatchBatch production and analysis. Start here.yes
mu2eshiftShifter account; DAQ shift toolsyes
mu2edaqDAQ expert accountyes
  • Same account on every node: the UID and the login environment are identical everywhere (~/.bashrc, aliases, the ~/bin tools).
  • Who may log in: mu2ebatch accepts everyone authorised for mu2eshift or mu2edaq.
  • Only these three can submit: Slurm rejects jobs from any other user.

Known issue: an interactive login as mu2ebatch prints a Kerberos Fail line, because the account has no group keytab yet. Jobs are not affected. If you need to ssh onward from the node, run kinit <username>@FNAL.GOV there first.

03Available disk areas

Every writable disk area is local to one node. There is no shared filesystem yet: a file written on worker-05 exists only on worker-05. The one area that is the same everywhere is /cvmfs, which is read-only.

Work under your own directory, /scratch/$USER and /data-local/$USER. This creates both on every node:

srun -N17 --chdir=/tmp mkdir -p /data-local/$USER /scratch/$USER

Nothing is backed up or cleaned automatically. Collect your results, then delete what you no longer need.

Mu2e software: CVMFS

The Mu2e software releases are served by CVMFS at /cvmfs/mu2e.opensciencegrid.org. It is mounted on every node, including the submit node, so a job sees the same software wherever it runs. It is read-only, and files are fetched and cached on the node the first time they are read. The first job on a node can therefore take a few seconds longer to start.

  • Always use the full path. ls /cvmfs can look empty, because a repository is mounted when it is first accessed. ls /cvmfs/mu2e.opensciencegrid.org mounts it.
  • Set up the environment in the job, not only in your login shell. Each job starts with a clean environment on the compute node:
#!/bin/bash
#SBATCH --job-name=mu2e-sim
#SBATCH --cpus-per-task=1
#SBATCH --mem=4G
#SBATCH --time=02:00:00
#SBATCH --chdir=/scratch
#SBATCH --output=/data-local/%u/%x-%j.out

source /cvmfs/mu2e.opensciencegrid.org/setupmu2e-art.sh
# then select your release as usual (muse setup …), and run mu2e
mu2e -c my_job.fcl -n 100

Check that CVMFS is visible from every compute node:

srun -N17 --chdir=/tmp bash -c \
  'ls /cvmfs/mu2e.opensciencegrid.org >/dev/null && echo "$(hostname -s) ok"' | sort

04Submission examples

Run all of these on the submit node, worker-01.

Check the cluster

sinfo                                       # mc1* up, 17 nodes idle
sinfo -N -l                                 # per-node CPUs, memory, state
srun -N1 hostname -s                        # one command on any node
srun -N17 --chdir=/tmp hostname -s | sort   # one task on every node

A batch job: hello.sbatch

#!/bin/bash
#SBATCH --job-name=hello
#SBATCH --cpus-per-task=4
#SBATCH --mem=8G
#SBATCH --time=00:10:00
#SBATCH --chdir=/data-local
#SBATCH --output=/data-local/%u/slurm-%x-%j.out

echo "job $SLURM_JOB_ID on $(hostname -s) with $SLURM_CPUS_PER_TASK CPUs"
srun sleep 5
sbatch hello.sbatch                # → Submitted batch job 56
squeue -u $USER
sacct -j 56 -X -o JobID,JobName,State,Elapsed,NodeList%20,ExitCode

The output directory must exist on the node that runs the job, so create it everywhere first (section 3). %u is your user name, %x the job name and %j the job id.

Many independent tasks (job array)

#!/bin/bash
#SBATCH --job-name=sweep
#SBATCH --array=0-99%34            # 100 tasks, at most 34 at once
#SBATCH --cpus-per-task=1
#SBATCH --mem-per-cpu=2G
#SBATCH --time=01:00:00
#SBATCH --chdir=/scratch
#SBATCH --output=/data-local/%u/sweep-%A_%a.out

./my_program --index "$SLURM_ARRAY_TASK_ID" \
             --out /data-local/$USER/sweep/result_$SLURM_ARRAY_TASK_ID.root

Multi-node job with its input copied to every node

#!/bin/bash
#SBATCH --nodes=4
#SBATCH --ntasks-per-node=8
#SBATCH --time=02:00:00
#SBATCH --output=/data-local/%u/multi-%j.out

sbcast /data-local/$USER/input.root /scratch/$USER/input.root
srun my_program /scratch/$USER/input.root

Interactive session

salloc -N1 -c8 --mem=16G --time=1:00:00
srun --pty bash

Watching and controlling jobs

TaskCommand
My jobssqueue -u $USER
Why is my job pending?squeue -j <id> -o "%i %T %r"

Cancel one, or all of minescancel <id> · scancel -u $USER
Today's historysacct -S today -X -o JobID,JobName,State,Elapsed,MaxRSS,NodeList%20
  • Memory is enforced. Go over your request and the job is killed (OUT_OF_MEMORY). With no request, a job gets 2000 MB per CPU.
  • Node sizes differ. Workers 02–16 have 16 CPUs; 17–18 have 32 (16 cores × 2 threads). Allocations are whole cores. Every node has about 60 GB of memory for jobs.
  • Always set --time. Short jobs with an accurate time start sooner, because the scheduler can fit them into gaps.

05Getting data back

Output stays on the compute node that ran the job. Getting it to your laptop takes two steps: from the node to worker-01, then from worker-01 to your machine.

Step 1 · From the compute node to worker-01

node=$(sacct -j <id> -X -n -P -o NodeList)     # -P: don't truncate the name

# look at one file
srun -w $node --chdir=/tmp cat /data-local/$USER/slurm-hello-<id>.out

# copy a directory back, streamed through Slurm (works for every account)
mkdir -p /data-local/$USER/collected
srun -w $node --chdir=/tmp tar -C /data-local/$USER -cf - myrun \
    | tar -C /data-local/$USER/collected -xf -

After an array or multi-node job, collect from every node:

for n in $(sinfo -h -N -o %N | sort -u); do
  srun -w $n --chdir=/tmp tar -C /data-local/$USER -cf - sweep 2>/dev/null \
    | tar -C /data-local/$USER/collected -xf -
done

Step 2 · From worker-01 to your machine

Run these on your own computer, with a valid ticket:

scp -J mu2eshift@g2gateway01.fnal.gov \
    mu2ebatch@mu2e-mc1-worker-01.fnal.gov:/data-local/mu2ebatch/collected/myrun/out.root .

rsync -av -e "ssh -J mu2eshift@g2gateway01.fnal.gov" \
    mu2ebatch@mu2e-mc1-worker-01.fnal.gov:/data-local/mu2ebatch/collected/ ./collected/

With the mc1 shortcut from section 1, the first command becomes scp mc1:/data-local/mu2ebatch/collected/myrun/out.root .

Clean up afterwards:

srun -N17 --chdir=/tmp rm -rf /data-local/$USER/myrun

··About

Mu2e software comes from CVMFS (/cvmfs/mu2e.opensciencegrid.org), provided on every node by the site installation. Slurm 26.05.4, built from SchedMD source for AlmaLinux 9 and 10, with MUNGE authentication and slurmdbd/MariaDB accounting on worker-01. The configuration is managed with Ansible in Mu2e/mu2edaq-batch-queues, which also holds the full user guide (docs/GETTING-STARTED.md, plus a PDF) and the operator documentation.

For cluster or account problems, contact the Mu2e DAQ experts. Include the job id and the output of scontrol show job <id>.

This page is a single self-contained HTML file with no external dependencies, so any static web server can host it.
